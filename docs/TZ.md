# ТЗ: API диалоговой генерации изображений

## 1\. Назначение

HTTP API для Telegram-бота, который генерирует изображения по тексту в диалоговом режиме. Пользователь отправляет реплику → получает картинку → следующей репликой уточняет её («сделай теплее», «добавь туман»), и так далее в пределах одной сцены.

Пет-проект для портфолио. Цели: продемонстрировать работу с LLM и LangChain, асинхронный Python-бэкенд, очереди задач. Приоритет — читаемость и простота.

## 2\. Стек

| Слой | Технология |
| :---- | :---- |
| API | FastAPI, motor (async MongoDB) |
| БД | MongoDB |
| Очередь | Celery \+ Redis (в воркере — pymongo, синхронно) |
| LLM | LangChain: GigaChat / Ollama, выбор через env |
| Генерация картинок | Kandinsky через FusionBrain API |
| Клиент | Telegram-бот на aiogram 3 (отдельный сервис) |
| Инфраструктура | Docker Compose, GitHub Actions |

## 3\. Ключевые решения

Приняты осознанно, пересмотру без явной необходимости не подлежат.

### 3.1 История диалога линейная

Никаких веток и откатов на произвольный узел. У сцены упорядоченный список изображений и текущее состояние. Дерево версий рассматривалось и отклонено.

### 3.2 Контекст сворачивается в SceneState

Вместо склеивания истории в растущий промпт держим структурное описание сцены. LLM работает как reducer: `(state, user_text) -> state`. Контекст фиксированного размера независимо от длины диалога.

class SceneState(BaseModel):

    subject: str \= ""

    setting: str \= ""

    style: str \= ""

    lighting: str \= ""

    palette: str \= ""

    composition: str \= ""

    details: list\[str\] \= \[\]

    negative: list\[str\] \= \[\]

Схема **плоская**: без `Union`, без `Optional`, без вложенных моделей — GigaChat не переваривает `anyOf`/`oneOf`/`allOf`. Пустая строка вместо `None`.

LLM возвращает **полное новое состояние, а не патч** — не нужен merge-слой, и модель стабильнее заполняет известную схему целиком.

### 3.3 Рендер промпта — чистая функция без LLM

`render_prompt(state) -> (prompt, negative)` детерминирован, тестируется обычным pytest, воспроизводится по сохранённому состоянию.

### 3.4 Только text2img, преемственность через seed

У Kandinsky по API доступен только режим `generate`, img2img нет и не требуется: полный промпт рендерится из состояния каждый раз, а `seed`, зафиксированный на сцену при создании, даёт визуальную преемственность между шагами.

### 3.5 Провайдеры через переменные окружения

def get\_llm() \-\> BaseChatModel:

    provider \= os.getenv("LLM\_PROVIDER", "gigachat")

    if provider \== "ollama":

        return ChatOllama(model=os.getenv("OLLAMA\_MODEL"), temperature=0.2)

    return GigaChat(credentials=os.getenv("GIGACHAT\_CREDENTIALS"), temperature=0.2)

Аналогично генератор картинок: интерфейс `submit(prompt, negative, seed, size)` и `poll(task_id)`. Фабрики остаются маленькими — LangChain уже даёт общий `BaseChatModel`, своих обёрток и реестров не нужно.

`temperature` 0.2–0.3: задача извлечения, не творчества.

## 4\. Модель данных

Коллекция `scenes`. Один документ \= одна сцена \= один диалог.

{

  "\_id": UUID,

  "user\_id": 123456789,

  "status": "PENDING",

  "seed": 42,                      \# фиксирован при создании сцены

  "scene\_state": {                 \# структура из 3.2, при создании пустая

    "subject": "", "setting": "", "style": "",

    "lighting": "", "palette": "", "composition": "",

    "details": \[\], "negative": \[\]

  },

  "images": \[                      \# история итераций, растёт через \$push

    {

      "user\_text": "закат над озером",   \# реплика пользователя

      "prompt": "sunset over a lake, ...", \# отрендеренный промпт

      "negative": "blurry, ...",

      "seed": 42,

      "url": "/files/images/2026/10/abc.png",

      "storage\_path": "images/2026/10/abc.png",

      "telegram\_file\_id": null,

      "sha256": "...",

      "width": 1024, "height": 1024, "size\_bytes": 812345,

      "at": ISODate

    }

  \],

  "image\_url": "/files/images/2026/10/abc.png",  \# дубль последней, для клиента

  "comment": "",                   \# отрендеренный промпт последней генерации

  "error": "",                     \# текст ошибки, чистится при новой реплике

  "created\_at": ISODate,

  "updated\_at": ISODate

}

Элемент `images` создаётся **сразу при запросе** с заполненным `user_text`, остальные поля дописывает воркер. Так история реплик сохраняется даже при неудачной генерации.

`image_url` — проекция последнего успешного элемента, чтобы клиент не разбирал массив. Единственный источник правды — сам массив.

`comment` содержит финальный отрендеренный промпт. Это первое, что нужно при отладке, и это же можно показать пользователю как «что бот понял». Другого назначения у поля нет — не превращать в свалку.

`error` обнуляется при каждой новой реплике, иначе старая ошибка будет висеть рядом с успешной картинкой.

### 4.1 Индексы

Mongo не создаст их сама. Заводятся при старте приложения:

scenes.create\_index("user\_id")

scenes.create\_index(\[("user\_id", 1), ("updated\_at", \-1)\])

scenes.create\_index("status")              \# для поиска зависших

scenes.create\_index("images.sha256", sparse=True)

## 5\. Статусы

PENDING ──► GENERATING\_SCENE ──► GENERATING\_IMAGE ──► DONE

                   │                      │

                   └──────► FAILED ◄──────┘

                                   ◄────── REJECTED

| Статус | Значение | Терминальный |
| :---- | :---- | :---- |
| `PENDING` | Задача создана, поставлена в очередь, воркер ещё не взял | нет |
| `GENERATING_SCENE` | LLM обновляет `scene_state` | нет |
| `GENERATING_IMAGE` | Запрос ушёл в генератор, идёт поллинг | нет |
| `DONE` | Картинка готова, `image_url` заполнен | да |
| `FAILED` | Техническая ошибка, текст в `error` | да |
| `REJECTED` | Промпт отклонён модерацией вендора, причина в `error` | да |

`REJECTED` отделён от `FAILED` намеренно: у Kandinsky своя модерация запросов, отказ — нормальный исход, а не сбой. Клиенту нужно показать разные сообщения.

`PENDING` отделён от `GENERATING_*`, чтобы отличать «ждёт в очереди» от «воркер взял и умер молча». Без этого зависшие сцены не отловить.

## 6\. API

Во всех ответах обязательные поля: `uuid`, `status`, `image_url`, `error`.

### 6.1 Создание сцены

POST /scenes/

{ "text": "закат над озером", "user\_id": 123456789 }

201 Created

{

  "uuid": "...", "status": "PENDING",

  "image\_url": null, "error": ""

}

Создаётся документ: `seed` генерируется случайно и фиксируется на всю жизнь сцены, `scene_state` пустой, в `images` кладётся первый элемент с `user_text`. Задача ставится в очередь.

### 6.2 Добавление реплики

POST /scenes/{uuid}/images

{ "text": "сделай теплее" }

202 Accepted

{ "uuid": "...", "status": "PENDING", "image\_url": "\<предыдущая\>", "error": "" }

**Если текущий статус не `DONE` — `409 Conflict`.** Это защищает от гонки: пользователь в Telegram нетерпелив и отправит вторую реплику, не дождавшись первой картинки. Без защиты воркер A вернулся бы со старым состоянием и перезаписал результат воркера B, потеряв реплику.

409 Conflict

{ "uuid": "...", "status": "GENERATING\_IMAGE", "image\_url": null,

  "error": "Предыдущая генерация ещё выполняется" }

> ⚠ **Побочный эффект, требующий решения.** При `FAILED` и `REJECTED` сцена тоже не `DONE`, то есть после любой неудачи она становится мёртвой — отправить новую реплику нельзя. Варианты: (а) разрешать POST при `FAILED`/`REJECTED`, то есть проверять «статус терминальный», а не «статус \= DONE»; (б) отдельный эндпоинт сброса. Вариант (а) предпочтительнее — одна строка условия.

При успешном приёме: `error` обнуляется, в `images` добавляется элемент с `user_text`, статус переводится в `PENDING`, ставится задача.

### 6.3 Чтение сцены

GET /scenes/{uuid}/

200 OK

{

  "uuid": "...",

  "status": "DONE",

  "image\_url": "/files/images/2026/10/abc.png",

  "error": "",

  "comment": "sunset over a lake, warm golden tones, ...",

  "scene\_state": { ... },

  "updated\_at": "2026-10-12T16:50:00Z"

}

Клиент опрашивает этот эндпоинт до терминального статуса. `scene_state` позволяет боту показать текущие параметры сцены, `updated_at` — обнаружить застрявшую задачу.

Интервал поллинга со стороны бота: 2 секунды, таймаут 180 секунд.

## 7\. Воркер

**Одна задача на оба сценария**, не две. Создание и обновление отличаются ровно тем, что в первом случае `scene_state` пустой. Пайплайн идентичен, две таски дублировали бы код и разошлись при первой же правке.

@celery.task(bind=True, max\_retries=2)

def process\_scene(self, scene\_uuid: str) \-\> None:

    \# 1\. GENERATING\_SCENE: LLM-цепочка обновляет scene\_state

    \# 2\. render\_prompt(state) \-\> prompt, negative

    \# 3\. GENERATING\_IMAGE: submit в генератор, поллинг до готовности

    \# 4\. сохранить файл, дописать элемент images, обновить image\_url

    \# 5\. DONE

### 7.1 Условные обновления

Каждый переход статуса — апдейт с проверкой текущего состояния в фильтре. Атомарно в пределах документа, транзакции не нужны.

res \= scenes.update\_one(

    {"\_id": uuid, "status": "GENERATING\_SCENE"},

    {"\$set": {"scene\_state": new\_state, "status": "GENERATING\_IMAGE"}}

)

if res.matched\_count \== 0:

    return  \# состояние ушло из\-под ног, тихо завершаемся

### 7.2 Защита от потери полей

Перед сохранением состояния сравнить старое и новое: если поле было непустым, обнулилось, а в реплике пользователя про него ни слова — вернуть старое значение. Иначе «сделай теплее» будет сбрасывать стиль.

### 7.3 Обработка ошибок

Любое исключение → статус `FAILED`, текст в `error`, задача не ретраится бесконечно. Отказ модерации вендора → `REJECTED` с причиной. Таймаут поллинга генератора → `FAILED`.

## 8\. Хранилище изображений

S3 не используется (нет бюджета). Протокол `Storage` с реализацией `LocalStorage` на `aiofiles`/`pathlib`, плюс `telegram_file_id` как бесплатная вторая копия.

class Storage(Protocol):

    async def put(self, key: str, data: bytes, content\_type: str) \-\> None: ...

    async def get(self, key: str) \-\> bytes: ...

    async def delete\_prefix(self, prefix: str) \-\> None: ...

Раскладка по датам: `images/{yyyy}/{mm}/{dd}/{uuid}.png`. Раздача наружу — через nginx (`X-Accel-Redirect`), не через FastAPI.

## 9\. Правила, которые легко нарушить

- **Байты не передаются в Celery.** Аргументы сериализуются в Redis. В таску уходит только `scene_uuid`, воркер сам достаёт данные.  
- **Картинки не хранятся в БД.** Только путь и метаданные. GridFS не использовать.  
- **base64 не кладётся в массив `images`.** Лимит документа 16 МБ съест за несколько генераций. Текстовая история до него не доберётся даже на тысяче итераций.  
- **Сначала файл, потом запись в БД.** Обратный порядок даёт документы, указывающие в пустоту. Запись файла — через временный файл и `os.replace()`.  
- **В БД относительный путь**, базовая директория в env. Иначе переезд на другой сервер \= массовый `update_many`.  
- **`file_path` из Telegram не хранить** — живёт около часа. Хранить `file_id`, он бессрочный. Скачивать сразу.  
- **Каскадов в Mongo нет.** Удаление сцены — сервисный метод: сначала файлы, потом документ.  
- **Схемы в Mongo нет.** Каждый документ проходит через Pydantic на входе и выходе репозитория. Сырые словари по коду не гуляют.  
- **`motor` в API, `pymongo` в воркере.** Не тащить async-клиент в синхронную таску.

## 10\. Тесты

- LLM-цепочки — через `FakeListChatModel` из `langchain_core`: детерминированно, без сети и без ключей в CI.  
- `render_prompt` и merge состояния — обычные unit-тесты без моков.  
- Репозитории — против поднятого в CI контейнера Mongo или `mongomock-motor`.  
- Сервисы — против фейковых репозиториев.  
- Интеграционные тесты с реальными внешними API в GitHub Actions не запускаются.

## 12\. Вне области задачи

Сознательно не делаем: древовидную историю версий, роутер интентов (классификацию реплик на `new_scene`/`edit`/`revert`), img2img и загрузку пользовательских референсов, веб\-интерфейс, мультиязычность промптов.
